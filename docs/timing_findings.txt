Key takeaways
-------------
1. Detection + tracking is ~100% of runtime. Every other stage (process, candidate, eval) is
   milliseconds -- the largest non-detection cost is ~1.3 s (only the 4K clip's candidate step).
   So "pipeline runtime" ~= "detection time".

2. The cost driver is FRAME COUNT, not resolution or file size. Because imgsz=1280 rescales every
   frame to the same working size, per-frame cost is roughly constant. Normalized (detect+track /
   frames):

     HIu4lM4B8hA_1 (352x288)   2.48 s/frame
     iMGR (960x720)            2.41
     gt1125_06 (4K)            1.86
     mKzCQKTHizw_1             1.77
     NmlzoaDcOuI_6             1.73
     mKzCQKTHizw_0             1.72
     1THkHYIQ_bY_0            1.70
     NmlzoaDcOuI_1            1.66

   ~1.7-2.5 s/frame across a 352x288 -> 4K range. The 4K / 40 MB clip is the slowest in ABSOLUTE
   terms only because it has the most frames (600); per frame it is actually FASTER than the two
   low-res clips. So source resolution and file size are NOT predictive -- frame count is.

3. Total detect+track across all 8 clips ~= 73 min on this CPU (multi-core).

4. Mild inversion worth a sentence: the low-res clips are slightly SLOWER per frame -- likely
   per-frame overhead / more spurious detections at upscaled low resolution, not the model itself.


Caveats
-------
- CPU-only; imgsz=1280 fixed; BoT-SORT tracking overhead is included (fused into detect+track,
  a single model.track call -- detection and tracking are not timed separately).
- Detection is run fresh (track cache bypassed), so the numbers are real compute, not cache hits.
- Description backends are separate from the above and dedup per track (only interaction
  participants are described): --fast (YOLO-World) ~0.2 s/crop; --detailed (moondream2)
  ~minutes/crop on CPU.
